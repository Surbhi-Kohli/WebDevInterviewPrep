# Bundlers Notes — Tree Shaking

---

# 1. What is Tree Shaking?

**Tree shaking** is a **build-time optimization** performed by modern bundlers to **remove code that is never used** from the final production bundle.

The term comes from the idea of shaking a tree so that only the **dead branches (unused code)** fall off.

The goal is to reduce:

* JavaScript bundle size
* Download time
* Parsing time
* Execution time

---

# 2. Why do we need Tree Shaking?

Suppose you have a utility library.

```javascript
// math.js

export function add(a, b) {
    return a + b;
}

export function subtract(a, b) {
    return a - b;
}

export function multiply(a, b) {
    return a * b;
}

export function divide(a, b) {
    return a / b;
}
```

Your application imports only one function.

```javascript
import { add } from "./math";

console.log(add(5, 10));
```

Without tree shaking

Final bundle contains

```text
✓ add
✓ subtract
✓ multiply
✓ divide
```

Even though only `add()` is used.

---

With tree shaking

Final bundle contains

```text
✓ add
```

Unused functions are removed.

---

# 3. What problem does Tree Shaking solve?

Imagine importing a huge library.

```javascript
import { debounce } from "lodash";
```

Without tree shaking

```text
Entire lodash

↓

500+ utility functions

↓

Included in bundle
```

With tree shaking

```text
Only debounce()

↓

Included
```

Much smaller bundle.

---


It happens before the final bundles are written.

# 5. How does Tree Shaking work?

Tree shaking depends on **static analysis**.

The bundler analyzes

```javascript
import

export
```

statements without executing the code.

Example

```javascript
// math.js

export function add(){}

export function subtract(){}

export function multiply(){}
```

Application

```javascript
import { add } from "./math";
```

Bundler builds a dependency graph.

```text
App.js

↓

Uses

↓

add()

↓

Does NOT use

subtract()

multiply()
```

Therefore

```text
Keep

↓

add()

Remove

↓

subtract()

multiply()
```

---

# 6. Why can the bundler know this?

Because ES Modules are **static**.

Static import

```javascript
import { add } from "./math";
```

The bundler knows exactly

* which file
* which export
* at build time

No code execution required.

---

# 7. Why is Tree Shaking difficult in CommonJS?

CommonJS uses

```javascript
const math = require("./math");
```

Later

```javascript
math[someVariable]()
```

or

```javascript
if(condition){

    require("./admin");

}
```

The bundler cannot always know

* what will be imported
* when
* which exports will be used

because `require()` is evaluated **at runtime**.

Therefore the safest option is often

```text
Include entire module
```

instead of trying to remove parts of it.

This is why **ES Modules enable reliable tree shaking**, while CommonJS generally does not.

# 8. ES Modules vs CommonJS

## ES Modules

```javascript
import { add } from "./math";
```

Bundler knows

```text
Only add() is required.
```

Can remove unused exports.

---

## CommonJS

```javascript
const math = require("./math");
```

Bundler only knows

```text
math object is required.
```

Cannot reliably determine which properties will be accessed later.

Usually keeps everything.

# 10. What if the module has side effects?

Example

```javascript
console.log("Application Started");

export function add(){}
```

Even if

```javascript
add()
```

is never called,

the module contains

```javascript
console.log(...)
```

Removing the module changes application behavior.

Bundler must keep it.

This is called a **side effect**.

---

## Side Effects

A side effect is code that does something merely by importing the module.

Examples

```javascript
console.log()
```

```javascript
window.localStorage.setItem(...)
```

```javascript
document.body.style.background = "red";
```

```javascript
fetch(...)
```

These cannot be removed safely.

---

# 11. sideEffects configuration

Many projects declare

```json
{
  "sideEffects": false
}
```

inside

```text
package.json
```

This tells bundlers

> Importing modules from this package does not execute code with side effects.

Therefore unused modules can safely be removed.

If some files do have side effects

```json
{
  "sideEffects":[
      "*.css"
  ]
}
```

This tells the bundler

Do not remove CSS imports.

# 12. Tree Shaking vs Minification

These are different optimizations.

## Tree Shaking

Removes unused code.

Example

Before

```javascript
function add(){}

function subtract(){}
```

After

```javascript
function add(){}
```

---

## Minification

Keeps the code but makes it smaller.

Before

```javascript
function add(a,b){

    return a+b;

}
```

After

```javascript
function a(b,c){return b+c}
```

Tree shaking removes code.

Minification compresses remaining code.

---

# 13. Tree Shaking vs Code Splitting

These are different optimizations.

## Tree Shaking

```text
Remove unused code.
```

---

## Code Splitting

```text
Split used code into multiple bundles.
```

Example

Without tree shaking

```text
main.js

contains

✓ add
✓ subtract
✓ multiply
```

With tree shaking

```text
main.js

contains

✓ add
```

---

Without code splitting

```text
main.js

5 MB
```

With code splitting

```text
main.js

dashboard.chunk.js

vendor.js
```

Tree shaking removes code.

Code splitting reorganizes code into multiple bundles.

# 14. How Different Bundlers Perform Tree Shaking

| Bundler     | Tree Shaking Support                                                              |
| ----------- | --------------------------------------------------------------------------------- |
| **Webpack** | Yes (production mode, ESM, plus a minifier like Terser to remove the unused code) |
| **Rollup**  | Excellent. Designed around ES Modules and performs aggressive tree shaking.       |
| **Vite**    | Uses Rollup for production, so it inherits Rollup's tree shaking capabilities.    |
| **Parcel**  | Built-in tree shaking using ES Module analysis.                                   |
| **Rspack**  | Similar to Webpack; supports tree shaking for ES Modules.                         |

Development builds usually skip or reduce tree shaking because fast rebuilds are more important than producing the smallest possible output.

---

# 15. Limitations of Tree Shaking

Tree shaking cannot always remove code.

Examples

Dynamic imports

```javascript
const module = await import(path);
```

Unknown runtime behavior

```javascript
require(variable)
```

Side-effectful modules

```javascript
console.log()
```

Reflection

```javascript
window[moduleName]()
```

The bundler removes only code it can **prove** is unused without changing behavior.

# Interview Summary

* **Tree shaking** is a **build-time optimization** that removes unused code from the final production bundle.
* It works best with **ES Modules** because `import` and `export` are **statically analyzable**, allowing bundlers to determine exactly which exports are used.
* **CommonJS** (`require`) is harder to tree shake because imports and property accesses are determined at runtime, making precise analysis difficult.
* Tree shaking is different from **code splitting** (which divides code into multiple bundles) and **minification** (which compresses the remaining code).
* Bundlers only remove code when they can prove it is unused and has **no side effects**. Modules that perform actions on import (such as logging, modifying global state, or importing CSS) are generally preserved unless explicitly marked as side-effect free.
* **Webpack, Rollup, Vite (via Rollup), Parcel, and Rspack** all support tree shaking in production builds, with Rollup generally regarded as the most aggressive because it was designed around ES Modules.


## Commonjs vs ES5 Tree shaking
Excellent question. These two examples are actually illustrating **two different problems** for tree shaking. Let's examine each one carefully.

---

# Example 1

```javascript
const math = require("./math");

math[someVariable]();
```

Suppose `math.js` is

```javascript
exports.add = () => {};
exports.subtract = () => {};
exports.multiply = () => {};
exports.divide = () => {};
```

Now imagine

```javascript
const someVariable = getOperationFromUser();

math[someVariable]();
```

At runtime

```javascript
someVariable = "add";
```

or

```javascript
someVariable = "multiply";
```

or

```javascript
someVariable = "divide";
```

The bundler **doesn't know** which one will be used.

It only sees

```javascript
math[someVariable]
```

It cannot determine

```text
Need add()

Need subtract()

Need divide()
```

Therefore the safest thing is

```text
Include entire math module
```

because removing any function could break the application.

---

## Compare with ES Modules

```javascript
import { add } from "./math";

add();
```

The bundler knows exactly

```text
Only add()
```

So it removes

```text
subtract()

multiply()

divide()
```

This is why ES Modules are tree-shakable.

---

# Example 2

```javascript
if(condition){

    require("./admin");

}
```

You asked:

> Isn't this dynamic import?

**It looks dynamic, but it is not the same as ES Module dynamic import.**

Let's compare.

---

## CommonJS require()

```javascript
if(condition){

    require("./admin");

}
```

Suppose

```javascript
condition = true;
```

Runtime executes

```javascript
require("./admin");
```

Suppose

```javascript
condition = false;
```

Nothing happens.

Notice

The **execution is conditional**, but

```javascript
require()
```

is still a **synchronous CommonJS API**.

When it runs, it expects the module to be immediately available.

There is no Promise.

There is no network fetch defined by the language.

---

## ES Module Dynamic Import

```javascript
if(condition){

    await import("./admin");

}
```

This is completely different.

`import()` returns

```javascript
Promise<Module>
```

The browser/runtime understands

```text
Need module

↓

Fetch module

↓

Execute

↓

Resolve Promise
```

This asynchronous behavior is defined by the JavaScript specification.

---

# Side-by-side comparison

## CommonJS

```javascript
const admin = require("./admin");
```

Characteristics

* synchronous
* immediately returns module
* no Promise
* no standard mechanism to fetch later
* designed for Node.js

---

## ES Modules

```javascript
const admin = await import("./admin");
```

Characteristics

* asynchronous
* returns Promise
* browser understands it
* supports lazy loading
* enables code splitting

---

# Then why can't webpack split this?

Good question.

Webpack is actually clever.

It may transform

```javascript
if(condition){

    require("./admin");

}
```

into another chunk **in some situations**.

However, this is **webpack-specific magic**, not CommonJS behavior.

Imagine another bundler.

It sees

```javascript
require("./admin")
```

Should it

* bundle it immediately?
* create another file?
* load later?

CommonJS never specifies.

So each bundler behaves differently.

---

# But ES Modules define this behavior

```javascript
await import("./admin")
```

is part of the JavaScript language itself.

Every modern bundler understands

> This module can be loaded asynchronously.

That's why modern tooling prefers ESM.

---

# Another subtle example

Suppose

```javascript
const moduleName = "./admin";

require(moduleName);
```

Now the bundler has no idea

```text
"./admin"

"./dashboard"

"./reports"

??
```

What if later

```javascript
moduleName = "./dashboard";
```

Now the bundler may have to include

```text
admin

dashboard

reports

everything
```

because it cannot know which one will actually be required.

Compare with ESM

```javascript
import "./admin";
```

The dependency is explicit and known at build time.

### One important clarification

Earlier I wrote that CommonJS "cannot" do code splitting. A more precise statement is:

* **CommonJS does not provide a standard language feature for asynchronous module loading**, so it does not naturally support code splitting or tree shaking.
* **Bundlers like Webpack can implement their own transformations for certain `require()` patterns**, but these are implementation-specific optimizations, not capabilities of CommonJS itself.
* **ES Modules were designed with static analysis and asynchronous `import()` in mind**, which is why all modern bundlers rely on ESM for robust tree shaking and code splitting.

This distinction is important in interviews because it shows you understand the difference between **what the JavaScript language guarantees** and **what a particular bundler chooses to implement**.
