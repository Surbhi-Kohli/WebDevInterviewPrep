# Loaders and Plugins in Bundlers

## First Principle

A bundler's job is much more than simply combining JavaScript files.

It must understand many file types:

```text
App.jsx

↓

App.css

↓

logo.png

↓

App.scss

↓

data.json

↓

config.yaml
```

The question is:

> **How does a bundler know what to do with each file?**

Different bundlers solve this differently.

* **Webpack** uses **loaders** and **plugins**.
* **Vite** has many capabilities built in and uses a **plugin system**.
* **Parcel** has a built-in asset pipeline with plugins internally.
* **Rollup** mainly uses plugins.

---

# The Build Pipeline

A simplified production build looks like

```text
Read source files
        │
        ▼
Resolve dependencies
        │
        ▼
Transform individual files
        │
        ▼
Dependency graph complete
        │
        ▼
Generate bundles
        │
        ▼
Optimize output
        │
        ▼
Write files to dist/
```

Notice there are two kinds of work:

1. Transforming **individual files**
2. Operating on the **entire build**

This is exactly where **loaders** and **plugins** differ.

---

# What is a Loader?

A loader transforms **one file (one module)** into another representation.

Think of it as

> **"Given this file, convert it into something the bundler understands."**

Example

```text
App.scss

↓

sass-loader

↓

App.css
```

Another example

```text
App.css

↓

css-loader

↓

JavaScript-understandable module
```

Loaders never know about the entire project.They only receive one file.

---

# What is a Plugin?

A plugin participates in the **overall build lifecycle**.

Think of it as

> **"Now that the bundler has processed everything, perform some build-wide task."**

Examples

```text
Generate HTML

Extract CSS

Compress bundles

Copy assets

Generate manifest

Define environment variables
```

A plugin can inspect

* every module
* every chunk
* every emitted file

before the build finishes.
Plugins can affect the entire build,while loaders transform individual files.

---

# Loader vs Plugin

| Loader                                 | Plugin                                          |
| -------------------------------------- | ----------------------------------------------- |
| Works on one file/module               | Works on the whole build                        |
| File transformation                    | Build orchestration                             |
| Runs while modules are being processed | Runs at different stages of the build lifecycle |
| Doesn't know about the whole project   | Can inspect all modules and output files        |
| Example: SCSS → CSS                    | Example: Generate `styles.css`                  |

## Plugin

After every file has already been processed

```text
App.css

Button.css

Navbar.css

Dashboard.css

↓

MiniCssExtractPlugin

↓

styles.css
```

The plugin coordinates the final output.
what about code splitting?Modern bundlers don't always produce one styles.css.

Suppose you have:Home Page, Admin Page, Dashboard Page

Webpack/Rollup/Vite might generate
```
main.css

dashboard.css

admin.css
```
When the user opens

Dashboard the browser downloads main.css ,dashboard.css

It never downloads

admin.css

So the plugin's job is more accurately:Collect processed CSS from all modules and emit one or more optimized CSS files based on the build strategy.
Why is it called a plugin?:Because it hooks into webpack's build lifecycle.

### Plugin lifecycle:
```
Start Build
      │
      ▼
Read files
      │
      ▼
Loaders process individual modules
      │
      ▼
Dependency graph complete
      │
      ▼
Plugins run
      │
      ├── Generate HTML
      ├── Extract CSS
      ├── Copy assets
      ├── Compress bundles
      └── Generate manifest
      │
      ▼
Write files to dist/
```
### Loader + Plugin in bundler
```
                Bundler

        ┌──────────────────┐
        │ Reads files       │
        └──────────────────┘
                  │
                  ▼
        ┌──────────────────┐
        │ Loaders          │
        │ Transform files  │
        └──────────────────┘
                  │
                  ▼
        ┌──────────────────┐
        │ Plugins          │
        │ Coordinate the   │
        │ overall build    │
        └──────────────────┘
                  │
                  ▼
        Final optimized output
```

# Why Can't a Loader Create styles.css?

Suppose css-loader is processing

```text
App.css
```

At that moment it has **never seen**

```text
Navbar.css

Button.css

Dashboard.css
```

It cannot combine files it doesn't know about.

Only after webpack finishes processing every module does it know

```text
Processed App.css

Processed Button.css

Processed Navbar.css

Processed Dashboard.css
```

Now a plugin can combine them.

# Common Loaders (Webpack)

## css-loader

Purpose

* Reads CSS
* Resolves `@import`
* Resolves `url(...)`
* Converts CSS into a module webpack understands

Example

```css
@import "./theme.css";

background:url("./logo.png");
```

---

## style-loader

Development only

Injects

```html
<style>

...

</style>
```

into the page.

Supports CSS Hot Module Replacement.

---

## sass-loader

Converts

```scss
.button{

    color:$primary;

}
```

↓

```css
.button{

    color:blue;

}
```

---

## babel-loader

Converts

```jsx
const App = () => <h1>Hello</h1>;
```

↓

```javascript
function App(){

}
```

Also converts modern JavaScript to older JavaScript if required.

---

## ts-loader

Compiles

```typescript
let x:number = 5;
```

↓

```javascript
let x = 5;
```

---

# Common Plugins (Webpack)

## MiniCssExtractPlugin

Development

```text
<style>
```

Production

```text
styles.css
```

Collects processed CSS from all modules and emits one or more CSS files.

---

## HtmlWebpackPlugin

Generates

```html
index.html
```

Automatically inserts

```html
<script src="main.js">

<link rel="stylesheet">
```

No need to manually edit HTML.

---

## CompressionPlugin

Creates

```text
main.js.gz

main.js.br
```

using Gzip or Brotli.

---

## CopyWebpackPlugin

Copies files

```text
public/

↓

dist/
```

without modification.

Useful for

* favicon
* robots.txt
* static assets

---

## DefinePlugin

Replaces

```javascript
process.env.API_URL
```

with

```javascript
"https://api.company.com"
```

during the build.

# Which Bundlers Use Loaders?

## Webpack

Webpack has explicit

* Loaders
* Plugins

Example

```text
App.scss

↓

sass-loader

↓

css-loader

↓

style-loader

↓

MiniCssExtractPlugin
```

Very configurable.

---

## Rollup

Rollup does **not** have loaders.

Everything is implemented through **plugins**.

Example

```text
rollup-plugin-postcss

↓

CSS support
```

```text
@rollup/plugin-typescript

↓

TypeScript
```

Plugins perform transformations that webpack would often split between loaders and plugins.

---

## Vite

Vite does **not** expose webpack-style loaders.

Instead it has

* built-in transforms
* plugin system

Example

```javascript
import "./App.css";
```

works immediately.

Internally

```text
Built-in CSS Plugin

↓

Process CSS

↓

Development

Inject CSS

────────────

Production

Extract CSS
```

No explicit css-loader configuration.

---

## Parcel

Parcel also avoids explicit loaders.

It has

* built-in asset pipeline
* plugin architecture

You simply write

```javascript
import "./App.scss";
```

Parcel figures out

* SCSS
* CSS
* images
* fonts

automatically.

---

## esbuild

No loaders.

Uses

* built-in transforms
* plugins

Very small plugin API.

Optimized for speed.

---

## Rspack

Webpack-compatible.

Supports

* webpack loaders
* webpack plugins

Very similar configuration.

---

# Interview Summary

### What is a loader?

A loader transforms an individual source file into a form the bundler can understand. Examples include compiling SCSS to CSS, JSX to JavaScript, or TypeScript to JavaScript.

### What is a plugin?

A plugin hooks into the bundler's build lifecycle to perform project-wide tasks after or during bundling, such as generating HTML, extracting CSS, compressing assets, or creating manifests.

### Which bundlers use loaders?

* **Webpack** and **Rspack** have an explicit loader concept.
* **Rollup**, **Vite**, **Parcel**, and **esbuild** rely on plugins and/or built-in processing instead of separate loaders.

### The easiest way to remember

| Question                                 | Answer                                                                  |
| ---------------------------------------- | ----------------------------------------------------------------------- |
| **Does it transform one file?**          | **Loader** (or the equivalent built-in transform in Vite/Parcel/Rollup) |
| **Does it coordinate the entire build?** | **Plugin**                                                              |
