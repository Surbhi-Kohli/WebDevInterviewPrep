# Bundlers Notes — Hashed Chunk Names

---

# 1. Why do bundlers add hashes to filenames?

During a production build, bundlers usually rename output files by adding a **content hash** to the filename.

Example

Instead of

```text
dist/

main.js
dashboard.js
vendor.js
styles.css
logo.png
```

the production build becomes

```text
dist/

assets/

main.8ab31c4a.js
dashboard.12fd8b91.js
vendor.72cd1e45.js
styles.2c91abf4.css
logo.f91d3a.png
font.91a82d.woff2
```

The hash is generated from the **contents of the file**, not its filename.

---

# 2. What is a Content Hash?

A content hash is a unique identifier calculated from the contents of a file.

Example

```javascript
function add(a,b){
    return a+b;
}
```

Suppose this generates

```text
main.a83bc1.js
```

Now you modify the code

```javascript
function add(a,b){
    return a+b+1;
}
```

The contents changed, so the hash changes.

```text
main.f91d2a.js
```

Same filename.

Different content.

Different hash.

---

# 3. Why do we need hashes?

The primary reason is **browser caching**.

Suppose version 1 of your application is deployed.

Browser downloads

```text
main.a83bc1.js
```

Browser stores it in cache.

Later you deploy a new version.

Without hashes

```text
main.js
```

Browser may think

> "I already have main.js."

and continue using the old JavaScript.

Users see stale code.

---

With hashes

Old deployment

```text
main.a83bc1.js
```

New deployment

```text
main.f91d2a.js
```

Browser sees a completely different filename.

```text
GET main.f91d2a.js
```

and downloads the latest version immediately.

---

# 4. Hashes Enable Long-Term Caching

Since filenames change whenever content changes, servers can safely tell browsers:

```http
Cache-Control: max-age=31536000
```

(one year)

Why?

Because

```text
main.a83bc1.js
```

will never change.

If the code changes,

the filename itself changes.

Old

```text
main.a83bc1.js
```

New

```text
main.f91d2a.js
```

This strategy is called **cache busting** or **cache invalidation using content hashes**.

---

# 5. Why hash chunks too?

Suppose your bundles are

```text
main.js
dashboard.chunk.js
vendor.js
```

If Dashboard changes,

without hashes

```text
dashboard.chunk.js
```

has the same filename.

Browser may continue using its cached version.

With hashes

Old deployment

```text
dashboard.12fd8b91.js
```

New deployment

```text
dashboard.98ac712e.js
```

Browser downloads the new Dashboard chunk automatically.

---

# 6. Which files usually receive hashes?

Almost every static asset.

| Asset              | Usually Hashed? |
| ------------------ | --------------- |
| JavaScript bundles | ✅               |
| JavaScript chunks  | ✅               |
| CSS files          | ✅               |
| Images             | ✅               |
| Fonts              | ✅               |
| SVGs               | ✅               |
| WebAssembly files  | ✅               |
| Videos (optional)  | Often           |

Example

```text
dist/

assets/

main.8ab31c4a.js
dashboard.12fd8b91.js
styles.2c91abf4.css
logo.f91d3a.png
Roboto.91bc2f.woff2
```

---

# 7. Does HTML get hashed?

Usually **No**.

Example

```text
index.html
```

The filename stays the same.

Instead, the contents of the HTML change.

Yesterday

```html
<script src="/assets/main.a123.js"></script>
```

Today

```html
<script src="/assets/main.f91d2a.js"></script>
```

The browser always requests

```http
GET /
```

↓

```text
index.html
```

The HTML points to the newest hashed assets.

---

# 8. Does the hash change every deployment?

**Not necessarily.**

The hash changes **only if the file's contents change.**

Suppose

Deployment 1

```text
main.8ab31c4a.js
dashboard.12fd8b91.js
vendor.72cd1e45.js
```

Only Dashboard code changes.

Deployment 2

```text
main.8ab31c4a.js
dashboard.98ac712e.js
vendor.72cd1e45.js
```

Notice

* `main.js` did not change.
* `vendor.js` did not change.
* Only `dashboard.js` received a new hash.

This is possible because modern bundlers generate **content hashes**, not deployment hashes.

---

# 9. Why is this important?

Without code splitting

```text
main.js (5 MB)
```

One small change

↓

Entire bundle changes

↓

Entire 5 MB downloaded again.

---

With code splitting

```text
main.8ab31.js

dashboard.12fd8.js

vendor.72cd1.js
```

Only Dashboard changes.

↓

Only

```text
dashboard.98ac71.js
```

is downloaded.

Everything else stays cached.

This is one of the biggest performance benefits of combining **code splitting** with **content hashing**.

---

# 10. What does the Manifest contain?

The manifest stores the mapping between original asset names and hashed filenames.

Example

```json
{
  "main.js": "assets/main.8ab31c4a.js",
  "dashboard.js": "assets/dashboard.12fd8b91.js",
  "vendor.js": "assets/vendor.72cd1e45.js",
  "styles.css": "assets/styles.2c91abf4.css",
  "logo.png": "assets/logo.f91d3a.png"
}
```

Servers and SSR frameworks use this mapping to generate the correct HTML.

---

# 11. Do all bundlers generate hashed filenames?

**Yes, all major modern bundlers support hashed filenames for production builds**, although the exact naming convention differs.

| Bundler     | Development                                              | Production                                              |
| ----------- | -------------------------------------------------------- | ------------------------------------------------------- |
| **Webpack** | Usually readable names (`main.js`)                       | Content-hashed filenames (`main.8ab31c4a.js`)           |
| **Vite**    | Native ES modules served directly (`App.jsx`, `main.js`) | Rollup generates hashed filenames (`index-8ab31c4a.js`) |
| **Rollup**  | Mostly used for production libraries/apps                | Commonly generates hashed chunks (`chunk-91bc2.js`)     |
| **Parcel**  | Readable development filenames                           | Automatically generates hashed filenames                |
| **Rspack**  | Similar to Webpack                                       | Content-hashed filenames                                |

Development builds usually avoid hashes because:

* Builds are frequent.
* Caching is disabled or minimal.
* Readable filenames make debugging easier.

Production builds use hashes to enable aggressive browser and CDN caching.

---

# 12. Naming conventions differ

Each bundler has its own default naming scheme.

Webpack

```text
main.8ab31c4a.js
dashboard.12fd8b91.js
```

Vite

```text
assets/

index-8ab31c4a.js
Dashboard-12fd8b91.js
```

Rollup

```text
chunk-91bc2.js
```

Parcel

```text
index.8ab31.js
```

The exact filename format isn't important.

The important idea is that **the filename includes a hash derived from its content**.

# Interview Summary

* Modern bundlers generate **content-hashed filenames** in production so browsers and CDNs can cache assets for a long time without serving stale content.
* The hash is based on the **contents of the file**, not on the deployment itself. A file's hash changes only when that file's contents change.
* Hashes are commonly applied to JavaScript bundles, JavaScript chunks, CSS files, images, fonts, and other static assets. `index.html` is typically **not hashed**; instead, its contents are updated to reference the latest hashed assets.
* Combining **code splitting** with **content hashing** allows browsers to reuse unchanged chunks (such as `vendor.js`) across deployments, downloading only the chunks whose content has actually changed. This significantly reduces bandwidth usage and improves load times for returning users.
* **Webpack, Vite (via Rollup), Rollup, Parcel, and other modern bundlers all support hashed filenames in production**, although their default naming conventions differ.
