# Bundlers Notes — Code Splitting & Lazy Loading

---

# 1. Why do we need Code Splitting?

Suppose our React application contains many pages.

```text
src/

App.jsx
Home.jsx
Dashboard.jsx
Admin.jsx
Reports.jsx
Settings.jsx
Charts.jsx
```

Without code splitting, the bundler creates one large bundle.

```text
dist/

main.js (5 MB)
```

When the user visits the homepage, the browser downloads the entire 5 MB, even though the user may never visit Dashboard, Admin, or Reports.

```text
User visits Homepage

        │
        ▼

Download main.js (5 MB)

        │
        ▼

Contains:
✓ Home
✓ Dashboard
✓ Admin
✓ Reports
✓ Charts
✓ Settings
```

Most of this JavaScript is never executed.

Problems:

* Longer initial page load
* More bandwidth usage
* Slower Time to Interactive (TTI)
* Poor performance on slow networks

---

# 2. What is Code Splitting?

**Code splitting** is a **build-time optimization** performed by the bundler.

Instead of producing one large bundle,

```text
main.js
```

the bundler generates multiple smaller bundles called **chunks**.

Example:

```text
dist/

main.js
dashboard.chunk.js
admin.chunk.js
reports.chunk.js
vendor.chunk.js
```

Now only `main.js` is downloaded initially.

Other chunks are downloaded only if required.

---

# 3. What is a Chunk?

A **chunk** is simply a separate JavaScript bundle.

Instead of

```text
One bundle

main.js
```

we now have

```text
main.js

dashboard.chunk.js

admin.chunk.js

vendor.chunk.js
```

Each chunk can be downloaded independently.

---

# 4. Who creates the chunks?

The **bundler** creates chunks.

Examples:

* Webpack
* Rollup
* Parcel
* Vite (uses Rollup during production)

The browser never creates chunks.

---

# 5. How does the bundler know where to split?

There are multiple strategies.

---

## Strategy 1 — Multiple Entry Points

Webpack configuration

```javascript
entry:{
    app:"./src/app.js",
    admin:"./src/admin.js"
}
```

Output

```text
app.js

admin.js
```

---

## Strategy 2 — Dynamic Import (Most Common)

Static import

```javascript
import Dashboard from "./Dashboard";
```

Bundler says

> Dashboard is required immediately.

So it includes Dashboard inside

```text
main.js
```

---

Dynamic import

```javascript
const Dashboard = await import("./Dashboard");
```

Bundler says

> This module can be placed into another chunk.

Output

```text
main.js

dashboard.chunk.js
```

This is the most common way to perform code splitting.

---

# 6. Static Import vs Dynamic Import

## Static Import

```javascript
import Dashboard from "./Dashboard";
```

Characteristics

* Static
* Known at build time
* Included inside main bundle
* Downloaded immediately

---

## Dynamic Import

```javascript
import("./Dashboard")
```

Characteristics

* Evaluated at runtime
* Returns a Promise
* Signals the bundler that this module can be split
* Downloads only when executed

---

# 7. Build Time vs Runtime

This is one of the most important interview concepts.

## Build Time

The bundler sees

```javascript
import("./Dashboard")
```

It decides

```text
main.js

dashboard.chunk.js
```

No browser exists yet.

Nothing has been downloaded.

The bundler has only created separate bundles.

This is **Code Splitting**.

---

## Runtime

User opens website.

Browser downloads

```text
main.js
```

Later

User clicks Dashboard.

React executes

```javascript
import("./Dashboard")
```

Browser sends

```http
GET dashboard.chunk.js
```

Downloads it.

Executes it.

Renders Dashboard.

This is **Lazy Loading**.

---

# 8. Difference between Code Splitting and Lazy Loading

Many engineers confuse these terms.

They are related but different.

## Code Splitting

Performed by

```text
Bundler
```

Purpose

Create multiple bundles.

Example

```text
main.js

dashboard.chunk.js

reports.chunk.js
```

Occurs

Build time.

---

## Lazy Loading

Performed by

```text
Browser

+

Runtime

+

React
```

Purpose

Download chunks only when required.

Occurs

Runtime.

---

## Relationship

Dynamic import serves two purposes.

During build

```javascript
import("./Dashboard")
```

tells the bundler

> This module may become another chunk.

During runtime

the same statement means

> Download that chunk now.

Thus,

**Dynamic import is the bridge between Code Splitting and Lazy Loading.**

---

# 9. How React performs Lazy Loading

React itself does **not** split code.

The bundler already created the chunks.

React simply waits until the component is needed.

Example

```javascript
import { lazy, Suspense } from "react";

const Dashboard = lazy(() => import("./Dashboard"));

function App() {

    return (

        <Suspense fallback={<h2>Loading...</h2>}>

            <Dashboard />

        </Suspense>

    );

}
```

---

## What React.lazy() does

```javascript
lazy(() => import("./Dashboard"))
```

means

> When Dashboard is first rendered,
> execute the dynamic import.

Dynamic import returns a Promise.

While waiting,

React displays

```jsx
<Suspense fallback={<Spinner/>}>
```

When the Promise resolves,

React renders Dashboard.

# 10. Can Lazy Loading happen without React?

Yes.

React is not required.

Example

```javascript
button.addEventListener("click", async () => {

    const dashboard = await import("./Dashboard.js");

    dashboard.show();

});
```

This works in plain JavaScript.

# 11. Vendor Code Splitting

Bundlers often create another chunk.

Example

```javascript
import React from "react";
import lodash from "lodash";
import axios from "axios";
```

Output

```text
main.js

vendor.js
```

Why?

Libraries change much less frequently than application code.

Browser can cache

```text
vendor.js
```

for a long time.

Next deployment

Only

```text
main.js
```

changes.

Users download much less.

# 14. How Different Bundlers Handle Code Splitting

| Bundler                | How chunks are created                                                                           |
| ---------------------- | ------------------------------------------------------------------------------------------------ |
| **Webpack**            | `import()` creates chunks. Webpack runtime loads them.                                           |
| **Rollup**             | `import()` creates chunks automatically.                                                         |
| **Vite (Development)** | No production bundles. Browser requests native ES modules individually from the Vite dev server. |
| **Vite (Production)**  | Uses Rollup. Generates chunks.                                                                   |
| **Parcel**             | Automatically creates chunks for dynamic imports.                                                |

# 15. Does Code Splitting work only with ES Modules?

## Yes.

Modern code splitting is fundamentally based on **ES Modules** and the `import()` syntax.

Static ESM import

```javascript
import Dashboard from "./Dashboard";
```

Dynamic ESM import

```javascript
import("./Dashboard")
```

The ECMAScript specification defines `import()` as an asynchronous operation that returns a Promise, making it ideal for lazy loading.

---

# 16. What about CommonJS?

CommonJS uses

```javascript
const dashboard = require("./Dashboard");
```

`require()` is **synchronous**.

When execution reaches this line, the module must already be available.

This means the bundler cannot naturally treat it as "download later."

Example

```javascript
if(admin){

    const dashboard = require("./Dashboard");

}
```

Even though it is inside an `if`, `require()` expects the module to be present immediately. A bundler usually includes it in the main bundle because there is no standard runtime protocol for fetching it later.

Some bundlers can recognize specific patterns and simulate asynchronous loading, but this is **bundler-specific behavior**, not something defined by CommonJS itself.

---

# 17. ESM vs CommonJS for Lazy Loading

| Feature                 | ES Modules   | CommonJS                                               |
| ----------------------- | ------------ | ------------------------------------------------------ |
| Static imports          | ✅ `import`   | ❌ (`require` is runtime)                               |
| Dynamic imports         | ✅ `import()` | ❌ No standard equivalent                               |
| Returns Promise         | ✅            | ❌                                                      |
| Standard code splitting | ✅            | ❌                                                      |
| Tree shaking            | ✅            | ❌ (generally not possible because exports are dynamic) |
| Native browser support  | ✅            | ❌                                                      |

# Interview Summary

* **Code Splitting** is a **build-time optimization** performed by the bundler. It creates multiple JavaScript bundles (chunks) from a single application.
* **Lazy Loading** is a **runtime strategy** where those chunks are downloaded only when they are needed.
* **Dynamic `import()`** is the bridge between the two: during the build it tells the bundler where it can split the code, and at runtime it triggers fetching of the corresponding chunk.
* **React does not perform code splitting itself**. It uses `React.lazy()` and `Suspense` to work with the chunks already created by the bundler.
* Modern code splitting relies on **ES Modules** because `import()` is part of the JavaScript standard. CommonJS's synchronous `require()` does not provide a standard mechanism for asynchronous loading, making code splitting and tree shaking much less effective.
