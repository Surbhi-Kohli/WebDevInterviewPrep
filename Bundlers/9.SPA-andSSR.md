# Consolidated Notes: SSR and Why React Apps Are SPAs

These notes combine your last two questions:

1. **Why does the server need to generate HTML in SSR, and why is final HTML not simply included in `dist/`?**
2. **Why are React applications called Single Page Applications?**

---

# 1. Normal React SPA

A typical client-rendered React app is built into:

```text
dist/
├── index.html
└── assets/
    ├── main-a81bc.js
    └── styles-f91ab.css
```

The `index.html` is usually a small HTML shell:

```html
<!doctype html>
<html>
  <head>
    <link rel="stylesheet" href="/assets/styles-f91ab.css" />
  </head>

  <body>
    <div id="root"></div>

    <script
      type="module"
      src="/assets/main-a81bc.js"
    ></script>
  </body>
</html>
```

The server returns this HTML file.

Then the browser:

```text
Downloads index.html
        ↓
Downloads React JavaScript
        ↓
React starts running
        ↓
React renders components inside #root
        ↓
React calls APIs for data
        ↓
React updates the DOM
```

The initial HTML often contains little actual page content:

```html
<div id="root"></div>
```

React creates the page in the browser.

---

# 2. Why is it called a Single Page Application?

A React application is commonly called a **Single Page Application**, or SPA, because the browser usually loads one main HTML document:

```text
index.html
```

After that, navigation is handled by JavaScript rather than by downloading a completely new HTML document for every route.

Suppose the user navigates between:

```text
/products
/cart
/profile
```

In an SPA, all these URLs may still use the same `index.html`.

```text
GET /products
    ↓
Server returns index.html

GET /cart
    ↓
Server returns index.html

GET /profile
    ↓
Server returns index.html
```

React Router reads the URL and chooses the component to display:

```jsx
<Routes>
  <Route path="/products" element={<Products />} />
  <Route path="/cart" element={<Cart />} />
  <Route path="/profile" element={<Profile />} />
</Routes>
```

So:

```text
URL changes
    ↓
React Router identifies the route
    ↓
React replaces part of the UI
    ↓
No full document reload
```

The browser remains on the same main HTML page.

---

# 3. React does not rebuild the entire HTML document

It is more accurate to say that React updates the application area inside the HTML document.

For example:

```html
<body>
  <div id="root">
    <!-- React controls this content -->
  </div>
</body>
```

When the user moves from Products to Cart:

```html
<div id="root">
  <Products />
</div>
```

becomes conceptually:

```html
<div id="root">
  <Cart />
</div>
```

React does not normally replace:

```html
<html>
<head>
<body>
```

It updates the relevant DOM elements inside its root.

A better definition is:

> A React SPA usually loads one HTML shell and then uses JavaScript to render and update the application content during navigation.

---

# 4. Traditional multi-page application versus SPA

## Traditional multi-page application

Suppose the user clicks Cart.

```text
Browser requests /cart
        ↓
Server generates or returns cart HTML
        ↓
Browser downloads a new HTML document
        ↓
Old document is replaced
        ↓
Page reload occurs
```

Each route may return a separate HTML document:

```text
/products → products HTML
/cart     → cart HTML
/profile  → profile HTML
```

---

## React SPA

```text
Browser initially downloads index.html
        ↓
React starts
        ↓
User clicks Cart
        ↓
React Router changes the URL
        ↓
React renders <Cart />
        ↓
No new full HTML document is downloaded
```

The route changes, but the application remains inside the same document.

---

# 5. How APIs fit into an SPA

In an SPA, the frontend and backend usually have separate responsibilities.

The frontend requests data:

```http
GET /api/products
```

The backend returns JSON:

```json
[
  {
    "id": 101,
    "name": "Keyboard",
    "price": 4999
  }
]
```

React then renders the data:

```text
React receives JSON
        ↓
React creates product components
        ↓
Browser DOM is updated
```

The backend usually does not return a new HTML page for every frontend route.

It returns data, while React controls the UI.

---

# 6. What problem does SSR solve?

In a purely client-rendered SPA, the first response may contain very little visible content:

```html
<div id="root"></div>
```

The browser must then:

```text
Download JavaScript
        ↓
Parse JavaScript
        ↓
Run React
        ↓
Call APIs
        ↓
Render page content
```

This can delay the moment when the user first sees meaningful content.

With **Server-Side Rendering**, the server renders the React components into HTML before sending the response.

For example, instead of sending:

```html
<div id="root"></div>
```

the server may send:

```html
<div id="root">
  <h1>Wireless Headphones</h1>
  <p>₹4,999</p>
  <button>Add to cart</button>
</div>
```

The browser can display this HTML immediately.

---

# 7. Why does the server generate HTML in SSR?

The server generates HTML because the final page may depend on information available only when the request arrives.

Examples include:

* requested URL
* product ID
* current database data
* logged-in user
* cookies
* permissions
* language
* location
* current inventory
* session data

Suppose the requests are:

```text
/products/101
/products/205
```

The server needs to return different content.

For product `101`:

```html
<h1>Wireless Headphones</h1>
<p>₹4,999</p>
```

For product `205`:

```html
<h1>Mechanical Keyboard</h1>
<p>₹7,499</p>
```

The server performs:

```text
GET /products/101
        ↓
Read product ID from URL
        ↓
Fetch product 101 from database/API
        ↓
Render <ProductPage product={product101} />
        ↓
Send product 101 HTML
```

Another request produces different HTML.

This is why the HTML is generated dynamically.

---

# 8. Why not put all final HTML pages in `dist/`?

You can put final HTML pages in `dist/` when all pages are known at build time.

That is called **Static Site Generation**, or SSG.

For example:

```text
/about
/contact
/docs/install
/docs/configuration
```

The build can generate:

```text
dist/
├── about/index.html
├── contact/index.html
├── docs/install/index.html
└── docs/configuration/index.html
```

That works because:

* routes are known during the build
* content changes infrequently
* there are a manageable number of pages

But it is not practical for routes such as:

```text
/products/1
/products/2
...
/products/10,000,000
```

It is also impossible to prebuild fully personalized pages such as:

```text
/account
/dashboard
/orders
```

because their content depends on the current user.

You should not generate this during the build:

```text
User A dashboard HTML
User B dashboard HTML
User C dashboard HTML
```

The server generates the page only after it knows who made the request.

---

# 9. What is inside `dist/` for an SSR application?

An SSR application still has build output, but it often contains two different builds.

```text
dist/
├── client/
│   ├── assets/
│   │   ├── main-a81bc.js
│   │   ├── dashboard-f91ab.js
│   │   └── styles-72ac.css
│   └── manifest.json
│
└── server/
    └── server-entry.js
```

## Client output

This is sent to the browser:

```text
JavaScript
CSS
images
fonts
lazy-loaded chunks
```

The client JavaScript is used for hydration and later interaction.

## Server output

This runs on the server:

```text
server-entry.js
```

It may expose logic similar to:

```js
render(url, requestData)
```

The server runs this code for each request to create the HTML response.

---

# 10. The server is not rebuilding the app for every request

This is an important distinction.

During deployment:

```text
Source React code
        ↓
Build process
        ↓
Generate server bundle and client bundle
```

During a user request:

```text
Request arrives
        ↓
Server runs already-built rendering code
        ↓
Passes URL and data to React
        ↓
React generates an HTML string
        ↓
Server sends HTML
```

The server does not run:

```bash
npm run build
```

for every request.

It executes an already-built server renderer with different inputs.

---

# 11. SSR can still use an HTML template

SSR may include an HTML template in the build output:

```html
<!doctype html>
<html>
  <head>
    <!--app-head-->
  </head>

  <body>
    <div id="root"><!--app-html--></div>

    <!--app-scripts-->
  </body>
</html>
```

The server fills the placeholders for each request.

For example:

```text
<!--app-head-->
        ↓
Title, metadata and CSS

<!--app-html-->
        ↓
Server-rendered React page

<!--app-scripts-->
        ↓
Client JavaScript assets
```

So SSR can still have an HTML shell in `dist`.

What is usually not stored in `dist` is the final personalized HTML response for every possible URL and user.

---

# 12. Complete SSR request flow

Suppose the user visits:

```text
/products/101
```

The flow is:

```text
Browser sends GET /products/101
        ↓
SSR server receives request
        ↓
Server reads URL and request context
        ↓
Server fetches product data
        ↓
Server renders React components to HTML
        ↓
Server inserts HTML into a template
        ↓
Server includes required CSS and JS assets
        ↓
Server returns complete HTML
        ↓
Browser displays HTML
        ↓
Browser downloads React client JavaScript
        ↓
React hydrates the page
```

---

# 13. What is hydration?

The HTML returned by SSR is initially visible, but it is not automatically a fully interactive React application.

For example, the server returns:

```html
<button>Add to cart</button>
```

The button is visible, but React must still attach:

```jsx
onClick={addToCart}
```

The browser downloads the client JavaScript, and React performs hydration:

```text
Existing server-rendered HTML
        +
React client code
        ↓
React connects components to the existing DOM
        ↓
Event handlers and state start working
```

Hydration does not normally recreate the complete page from nothing.

It connects React behavior to the HTML already produced by the server.

---

# 14. Can an SSR React application still behave like an SPA?

Yes.

This is a key point:

> SSR and SPA are not complete opposites.

A React application may use SSR for the first request:

```text
GET /products/101
        ↓
Server returns rendered HTML
```

After hydration, internal navigation may happen on the client:

```text
User clicks Cart
        ↓
Client-side router changes route
        ↓
React renders Cart
        ↓
No full page reload
```

So an application can be:

```text
Server-rendered on initial load
+
SPA-like during later navigation
```

Frameworks such as Next.js and Remix commonly use this hybrid model.

---

# 15. SPA describes navigation behavior

SPA does not necessarily mean:

```text
The server can never generate HTML.
```

It mainly means:

```text
After the application is loaded,
navigation usually does not replace
the entire HTML document.
```

The initial page may be:

* client-rendered
* server-rendered
* statically generated

After the application becomes active in the browser, navigation can still behave like an SPA.

---

# 16. CSR, SSG and SSR comparison

| Approach        | When page HTML is generated | Typical first response          | Can later navigation behave like an SPA? |
| --------------- | --------------------------- | ------------------------------- | ---------------------------------------- |
| CSR SPA         | In the browser              | Generic HTML shell              | Yes                                      |
| SSG             | During build                | Pre-generated page HTML         | Yes                                      |
| SSR             | For each request            | Dynamically generated page HTML | Yes                                      |
| Traditional MPA | Usually on each request     | Complete page HTML              | Usually full-page navigation             |

# 17. Simple mental models

## Client-rendered SPA

```text
Server sends HTML shell
        ↓
Browser runs React
        ↓
React creates page
        ↓
React handles navigation
```

## SSR React application

```text
Server runs React first
        ↓
Server sends rendered HTML
        ↓
Browser displays page
        ↓
React hydrates it
        ↓
React handles later navigation
```

## SSG React application

```text
Build process runs React
        ↓
HTML pages are saved in dist
        ↓
Static server returns them
        ↓
React hydrates them
```

---

# Final Summary

A typical React SPA is called a **Single Page Application** because one main HTML document is loaded, while React updates the page content and handles route changes without downloading a new complete HTML document for every navigation.

In a client-rendered SPA, the server usually sends a generic `index.html`, and React builds the visible page in the browser.

In SSR, the server generates HTML because the page may depend on request-time information such as the URL, user session, permissions or current database data. That final HTML cannot always be created once during the build and stored in `dist/`.

SSR applications still have build output. It commonly includes:

```text
Client assets
+
Server rendering code
+
Possibly an HTML template
```

The server executes the built rendering code for each request and creates the final HTML response.

After the browser receives SSR HTML, React hydrates it and can handle later navigation like an SPA. Therefore, an application can use both SSR and SPA-style navigation.
