# Consolidated Notes: Bundler Manifest

These notes combine your last four manifest-related questions:

1. **What is a manifest, why is it needed, and who saves it?**
2. **Is the server using it a backend server or a frontend server?**
3. **Where is `build.manifest: true` configured in Vite?**
4. **Why are manifests more important when a server generates HTML dynamically?**

---

# 1. What is a manifest?

A manifest is a **build-generated lookup file** that describes the assets produced by the frontend build.

Suppose your source contains:

```text
src/
├── main.tsx
├── Dashboard.tsx
├── styles.css
└── logo.png
```

After a production build, the bundler may produce:

```text
dist/
├── index.html
├── manifest.json
└── assets/
    ├── main-a81bc3.js
    ├── Dashboard-f29ab7.js
    ├── styles-91df20.css
    └── logo-72ab11.png
```

The filenames contain content hashes for caching.

A simplified manifest may look like:

```json
{
  "src/main.tsx": {
    "file": "assets/main-a81bc3.js",
    "css": [
      "assets/styles-91df20.css"
    ],
    "imports": [
      "assets/vendor-61a22c.js"
    ]
  },
  "src/Dashboard.tsx": {
    "file": "assets/Dashboard-f29ab7.js"
  }
}
```

It answers questions such as:

```text
What did src/main.tsx become after the build?
```

Answer:

```text
assets/main-a81bc3.js
```

A useful mental model is:

> The manifest connects logical source entries to their actual production assets.

---

# 2. Why is a manifest needed?

Production asset filenames often contain hashes:

```text
main-a81bc3.js
styles-91df20.css
```

Those hashes change when the file content changes.

For example:

```text
Previous build:
main-a81bc3.js

New build:
main-f72da1.js
```

A server generating HTML cannot safely hardcode:

```html
<script src="/assets/main-a81bc3.js"></script>
```

because the next build may produce a different name.

Instead, the server can read the manifest:

```json
{
  "src/main.tsx": {
    "file": "assets/main-f72da1.js"
  }
}
```

and generate:

```html
<script
  type="module"
  src="/assets/main-f72da1.js"
></script>
```

The manifest therefore prevents:

* broken asset references
* `404 Not Found` errors
* stale hashed filenames
* manual HTML updates after every build

---

# 3. Who generates the manifest?

The **bundler or build tool** generates it during the production build.

Examples:

| Build tool | How manifest generation works                            |
| ---------- | -------------------------------------------------------- |
| Vite       | Built-in `build.manifest` option                         |
| Webpack    | Usually through a plugin such as `WebpackManifestPlugin` |
| Rollup     | Through configuration or plugins                         |
| Frameworks | May generate their own internal build manifests          |

The general build flow is:

```text
Source code
    ↓
Bundler resolves dependencies
    ↓
Tree shaking
    ↓
Code splitting
    ↓
Minification
    ↓
Content hashing
    ↓
Assets generated
    ↓
Manifest generated
```

---

# 4. Who saves the manifest?

The bundler writes it into the build output directory.

For example:

```text
dist/
├── manifest.json
└── assets/
    ├── main-a81bc3.js
    └── styles-91df20.css
```

It is normally:

* not stored in a database
* not created by the browser
* not created separately at runtime
* not something the user downloads manually

It is simply another build artifact.

When the application is deployed, the build output may be copied to:

```text
Nginx
S3
CloudFront
Node server
container image
deployment artifact storage
```

The manifest is stored alongside or near the generated frontend assets.

Some deployment setups keep the manifest accessible only to the backend rather than publicly exposing it.

---

# 5. Does the browser normally read the manifest?

Usually, **no**.

The browser normally receives HTML that already contains the final asset paths:

```html
<link
  rel="stylesheet"
  href="/assets/styles-91df20.css"
/>

<script
  type="module"
  src="/assets/main-a81bc3.js"
></script>
```

The browser then downloads those files directly.

Typical flow:

```text
Browser
    ↓
GET /
    ↓
Receives HTML
    ↓
HTML references main-a81bc3.js
    ↓
Browser requests main-a81bc3.js
```

The browser does not need to ask:

```text
What did main.tsx become?
```

That lookup has already been performed by either:

* the bundler while generating static `index.html`, or
* the backend while dynamically generating HTML

---

# 6. Which “server” reads the manifest?

The word **server** can mean several things, so the distinction matters.

## Static web server

Examples:

```text
Nginx
Apache
S3
CloudFront
Netlify
static hosting
```

A static web server usually just serves files from `dist/`.

For a normal Vite SPA:

```text
Browser
    ↓
GET /
    ↓
Nginx returns dist/index.html
    ↓
Browser reads hashed asset URLs
```

The static server normally does **not** need to interpret the manifest.

Why not?

Because Vite already generated `index.html` with the correct asset names:

```html
<script
  type="module"
  src="/assets/main-a81bc3.js"
></script>
```

---

## Backend or SSR server

Examples:

```text
Express
NestJS
Spring Boot
Django
Rails
Laravel
Next.js SSR server
Remix server
```

These servers may generate HTML at request time.

For example:

```text
Browser
    ↓
GET /dashboard
    ↓
Express or SSR server
    ↓
Server renders HTML
    ↓
Server must include correct JS and CSS files
```

This server may read the manifest to discover:

```text
src/main.tsx
    ↓
assets/main-a81bc3.js
```

Therefore, when we say:

> The server reads the manifest

we are generally talking about a **backend or SSR server that generates HTML**, not a static server that merely returns an already-generated `index.html`.

---

# 7. Static SPA: why a manifest may not be needed at runtime

Suppose Vite creates:

```text
dist/
├── index.html
└── assets/
    ├── main-a81bc3.js
    └── styles-91df20.css
```

Vite also writes the filenames directly into `index.html`:

```html
<!doctype html>
<html>
  <head>
    <link
      rel="stylesheet"
      href="/assets/styles-91df20.css"
    />
  </head>
  <body>
    <div id="root"></div>

    <script
      type="module"
      src="/assets/main-a81bc3.js"
    ></script>
  </body>
</html>
```

The deployment flow is:

```text
Vite build
    ↓
Vite knows generated filenames
    ↓
Vite writes them into index.html
    ↓
Deploy entire dist/
    ↓
Static server returns index.html
```

There is no runtime lookup required.

The browser gets exactly the asset names it needs.

Therefore a standalone SPA often does not need `manifest.json`.

# 8. Why manifests become important for dynamically generated HTML

This was your key question:

> Why do manifests become more important when a server generates HTML dynamically?

The important distinction is:

## Static HTML

The bundler generates the HTML.

```text
Bundler creates:
index.html
main-a81bc3.js
styles-91df20.css
```

Because the bundler created all of them, it can directly put the correct filenames into `index.html`.

```text
Bundler already knows:
main.tsx → main-a81bc3.js
```

No separate runtime lookup is needed.

---

## Dynamically generated HTML

A backend server generates the HTML later, possibly when the request arrives.

For example:

```js
app.get("/", (req, res) => {
  res.send(`
    <html>
      <body>
        <div id="root"></div>
        <script src="???"></script>
      </body>
    </html>
  `);
});
```

The backend knows the logical frontend entry:

```text
src/main.tsx
```

But the frontend build generated:

```text
assets/main-a81bc3.js
```

The backend did not choose that hash and cannot predict the next one.

So it reads the manifest:

```json
{
  "src/main.tsx": {
    "file": "assets/main-a81bc3.js",
    "css": [
      "assets/styles-91df20.css"
    ]
  }
}
```

Then it generates:

```html
<link
  rel="stylesheet"
  href="/assets/styles-91df20.css"
/>

<script
  type="module"
  src="/assets/main-a81bc3.js"
></script>
```

The manifest acts as a bridge between:

```text
What the backend knows:
src/main.tsx
```

and:

```text
What the bundler produced:
assets/main-a81bc3.js
```

# 9. SSR example

Suppose the user requests:

```text
/dashboard
```

The SSR server renders:

```jsx
<Dashboard />
```

It sends server-rendered HTML so the page is visible immediately.

But the browser also needs JavaScript for hydration and CSS for styling.

The required build assets might be:

```text
Dashboard-f29ab7.js
Dashboard-81bc20.css
vendor-a66de1.js
```

The server needs to know which files belong to the Dashboard route or entry.

Build metadata such as a manifest may tell it:

```json
{
  "src/Dashboard.tsx": {
    "file": "assets/Dashboard-f29ab7.js",
    "css": [
      "assets/Dashboard-81bc20.css"
    ],
    "imports": [
      "assets/vendor-a66de1.js"
    ]
  }
}
```

The server then returns HTML similar to:

```html
<html>
  <head>
    <link
      rel="stylesheet"
      href="/assets/Dashboard-81bc20.css"
    />
  </head>

  <body>
    <div id="root">
      <!-- Server-rendered Dashboard HTML -->
    </div>

    <script
      type="module"
      src="/assets/vendor-a66de1.js"
    ></script>

    <script
      type="module"
      src="/assets/Dashboard-f29ab7.js"
    ></script>
  </body>
</html>
```

Frameworks such as Next.js usually manage this automatically using internal build metadata. You may not manually open a manifest, but the same underlying problem still has to be solved.

# 10. Where is manifest generation configured in Vite?

In:

```text
vite.config.js
```

or:

```text
vite.config.ts
```

Example:

```ts
import { defineConfig } from "vite";

export default defineConfig({
  build: {
    manifest: true
  }
});
```

Then:

```bash
npm run build
```

generates the production assets and the manifest.

Depending on the Vite version and configuration, the manifest is placed inside the build output, commonly under a Vite-specific location such as:

```text
dist/.vite/manifest.json
```

The important point is that `build.manifest` tells Vite:

> Along with the normal production assets, generate build metadata that maps source entries to their output files.

---

# 11. When should `build.manifest` be enabled?

It is most useful when Vite is integrated with:

* Express
* Laravel
* Django
* Rails
* Spring Boot
* ASP.NET
* custom SSR
* another backend that generates HTML

Example:

```text
Backend template
    ↓
Needs frontend entry
    ↓
Reads Vite manifest
    ↓
Finds hashed JS and CSS
    ↓
Writes correct tags into HTML
```

For a standalone static SPA, it is often unnecessary because Vite already generates an `index.html` containing the correct references.

---

# 12. Manifest and source maps are unrelated

A manifest is not a source map.

## Manifest

Maps logical files or entries to built assets:

```text
src/main.tsx
    ↓
assets/main-a81bc3.js
```

Used by:

* backend servers
* SSR frameworks
* deployment tooling
* asset lookup logic

---

## Source map

Maps generated code positions back to original source code:

```text
main-a81bc3.js
line 1, column 17820
    ↓
src/App.tsx
line 42, column 7
```

Used by:

* browser developer tools
* Sentry
* debugging and monitoring tools

The simplest distinction is:

> Manifest: “What is the production filename?”

> Source map: “Where did this generated code come from?”

# Final Mental Model

## Static Vite SPA

```text
npm run build
    ↓
Vite generates hashed assets
    ↓
Vite puts their names into index.html
    ↓
Deploy dist/
    ↓
Static server returns index.html
    ↓
Browser downloads referenced assets
```

Manifest is usually unnecessary at runtime.

---

## Backend or SSR application

```text
npm run build
    ↓
Vite generates hashed assets
    ↓
Vite generates manifest
    ↓
Deploy assets + manifest
    ↓
Request reaches backend/SSR server
    ↓
Server reads manifest
    ↓
Server generates HTML with correct asset URLs
    ↓
Browser downloads those assets
```

## Core takeaway

A manifest is needed when the code generating the HTML does not already know the unpredictable hashed names created by the frontend build.

It provides the mapping:

```text
Logical frontend entry
        ↓
Actual production JS/CSS/chunks
```

For static SPAs, the bundler already inserts that information into `index.html`. For backend-rendered or SSR applications, the server may need the manifest so it can insert the correct production assets while generating HTML dynamically.
